# Performance, responsive UI and private registration — 13 November 2026

This checkpoint implements sections 2–4 of [the upgrade request](FIREBASE_UPGRADE_SPEC.md) in the existing React/Nest/PostgreSQL application. It is local development work. The [production deployment hold and outstanding environment checks](PRODUCTION_STATUS.md) still apply.

## What caused repeated waiting

Source inspection and a disposable PostgreSQL fixture identified full-event registration reads (including every guest's ticket metadata), unbounded ticket/candidate/independent-attendee lists, repeated filtering over all guests for each student, and cache invalidation that did not update every mounted consumer. Late responses could also outlive a mutation. Navigation already used lazy modules; it lacked route/data prefetching. No production trace, hosted latency or cold-start measurement was available, so these are verified local causes, not a claim to have diagnosed every hosted delay.

- Registration, ticket, eligible issuance-candidate and independent-attendee screens now use server-filtered **50-row cursor pages**. Search is debounced 250 ms; changing filters resets the cursor and hidden ticket selections. Only one next page is prefetched. Student selection has a paged search so students beyond the first page remain reachable. Full export/import compatibility endpoints remain available.
- Student-page guest counts use a bounded grouped query. Guest pages include only their linked students. Additive migration **16** adds `(event_id, id)` indexes to students, guests, attendees and tickets; it has been exercised only on disposable QA databases. Hosted databases remain at 11.
- Each signed-in Client has its own memory cache, keyed by full event path/query, capped at 100 entries with five-minute retention. Freshness is five seconds for tickets/users, ten seconds for ordinary lists/reports, thirty seconds for event lists/settings and sixty seconds for categories/entrances/templates. Concurrent reads share a promise; fresh navigation/prefetch reuses it. Auth/public capabilities and binary downloads remain uncached.
- Mounted views revalidate stale data while visible, on focus and after mutations. Existing rows stay visible with explicit refresh/error notices; failed refreshes retain previously loaded rows. Failed saves retain form input. Late pre-mutation/logout responses cannot refill the cache or reach consumers.
- Logout, denied access and changed identity/organization/role/assignment revisions clear private data. The uncached session check runs every thirty seconds while visible, with a fifteen-second focus cooldown. Assignment changes remount the workspace and close old private forms. Server authorization applies immediately on every operation; an idle screen may display its prior data until the next check. There is no offline authorization or persistent attendee cache.

## Measurements and limits

The integration fixture contains 220 additional students and 220 guests. `tmp/registration-performance.json` records serialized response sizes and one local elapsed-time sample for the old overview and new first guest page. It contains no attendee data. Local timing includes the API/database request and is not a stable benchmark; fixture and cache unit tests also verify bounded pages and request counts. See [production status](PRODUCTION_STATUS.md) for the final measured values and test results.

Eight concurrent reads of the same resource result in one request; eight more reads while fresh result in no additional requests. Browser checks confirm the workspace and Events page share their initial event-list request. Automatic visible refreshes deliberately add requests after freshness expires. Background/hidden tabs skip those checks; prefetch is bounded and permission-scoped. These changes reduce repeat work and transfer size but do not promise zero API traffic.

Route modules remain split and now preload on navigation hover/focus. Both Vercel configs give immutable public caching only to hashed static asset names. HTML/deep links, auth, attendee and ticket responses use `no-store`; API and missing-asset paths retain real 404 handling. The bundled `/scan/` server applies the same hashed-asset boundary. Vercel header behavior still needs hosted verification at the authorized deployment.

Cloud Run is still configured with zero minimum instances. A first request after scale-to-zero or a new revision can wait for container startup, Nest/Prisma initialization and database connection establishment. Client caching cannot remove that first wait. No warm instance, paid cache, provider subscription or billing setting was enabled. Increasing minimum instances would add idle compute cost and requires the owner's billing decision plus actual hosted measurements. The existing [cost worksheet](PRODUCTION_COSTS.md) documents estimates and assumptions; these local tests do not revise it. Write/import planners still validate the complete event under its lock, and large exports/PDF rendering still need representative production load testing.

## Primary student registration form

In **Students & Invitations**, create/rotate a student's private **Invitation link**, review the reason/confirmation and copy its once-shown URL. That link opens **Open registration form** without an administrator login. Excel remains a compatibility option.

The capability identifies an already eligible active student. Knowing a Student ID grants no access. The student can update their own name/email/phone and configured student fields, select a guest quantity, and enter the configured details for each guest. They can view, amend or cancel only guests belonging to that capability. The Student ID, sender, limits and administrator overrides cannot be changed through the form.

**Quantity means new guest tickets, excluding the student's own ticket.** An eligibility/student record does not itself create an admission ticket. Event **Invitation limits ? Guests per student** controls the allowance: limit 1 offers 1; limit 2 offers 1 or 2; limit 3 offers 1, 2 or 3. Active existing guests consume that allowance: with two existing guests and a limit of three, only one can be added. An organizer's existing reason-audited individual allowance remains an explicit override. The form also offers 0 to update only the student's details. A single submission is capped at 50 guests; larger configured allowances can be filled in separate submissions while capacity remains.

Event/category/per-student/category-per-student limits, active registrations, permitted categories, required custom fields, deadlines and event lifecycle checks are enforced server-side. Public additions reserve a place even with automatic ticket generation off: active registered attendees count once, live/used ticket places remain counted, and registrations already represented by their live ticket are not double-counted. A full event/category rejects growing public registration batches atomically. Existing organizer management/import override behavior is preserved. Admission and issuance continue to use the current server's locked checks; a cached count or successful registration is never permission to admit someone or bypass issuance.

The existing event lock serializes these operations with admin changes, ticket issuance and check-in. A stable request key plus an immutable, content-bound receipt makes retries/concurrent identical submissions return the same result. Any failed guest/profile/capacity validation rolls back the whole batch. Public amendments stop at the registration deadline; checked-in guests cannot be amended and category changes after live issuance require the organizer. Allowed detail edits preserve IDs and QR credentials; printed ticket files remain snapshots. Cancellation retains admission/history rules. Optional server-verified Turnstile applies to the batch form as well as the existing add/cancel flows; tests mock its provider, and hosted keys/settings remain the owner's setup task.

No hosted schema, frontend, API address, email flag, database source, original SQLite or Streamlit application was changed.
